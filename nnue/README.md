# NNUE net (pawnstar-rs)

`pawnstar-v20.bin` is the shipped evaluation network, new in **release 2.0.0**: a bullet-trained
perspective net, 1024-wide feature transformer with 8 **horizontally mirrored** king buckets and 8
material output heads, **trained entirely on Leela Chess Zero self-play data**, in the shared
Reckless NNUE container `RNNUE1` — a 64-byte self-describing header (see
`src/nnue.rs::NetHeader`) and a 12,617,760-byte payload, with a CRC-64/XZ over each. It is
**byte-identical to the net shipped by the C++ and Go engines** — all three are cross-loadable
and produce bit-identical evaluations from it.

| | Value |
|---|---|
| SHA-256 | `c8a29b328849cd1ea60c65f5d3dea84f585f404037ec026c44a94e1174b1cc34` |
| file size | 12,617,824 bytes (a 64-byte header and a 12,617,760-byte payload) |
| `format_version` | 2 |
| `king_bucket_map_crc` | `0x0A20060D4E9586E0` |
| `bench` signature | **5,617,906** nodes at depth 13, single-threaded (`tests/bench_golden_test.rs`) |

Measured against v12, the net it replaces: **+9.99 Elo at 8+0.08** over 8,000 games and **+1.13 at
12+0.12** over 12,000 games — a gain at the faster time control and level at the slower one. The
architecture is the shared shape v12 was already being moved onto; what changed is the training
data.

The container is the one every reckless-technology chess engine reads; the `reckless-nnue` skill is
its specification. **By default** this engine is compiled for the shape v20 needs — king
mirroring on (`flags = 1`) and eight output heads (`output_buckets = 8`) — and a net that asks
for anything else is refused. The retired v12 shape still builds from the same tree; see below.

## The training data, and the notice it obliges

v20's training pool is the **Leela Chess Zero self-play training data**
(<https://storage.lczero.org/files/training_data/>) and nothing else: 6,143,698,748 positions, **62.83%
from run `test91` and 37.17% from run `test60`**. The archives are published under the **Open Database
License 1.0** (<http://opendatacommons.org/licenses/odbl/1.0/>), their contents under the **Database
Contents License 1.0** (<http://opendatacommons.org/licenses/dbcl/1.0/>).

A trained net is an ODbL **"Produced Work"**, so shipping `pawnstar-v20.bin` obliges a notice naming
the source. That notice is **[../THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md)**, which carries
the attribution line verbatim for each run; the engine prints a condensed form on the `license`
command, so a release binary downloaded on its own carries it too.

Two things the notice is explicit about, and this file repeats because it is where people look:

- **The obligation is the notice.** ODbL does **not** require the network itself to be
  ODbL-licensed - its share-alike reaches derivative *databases*, not Produced Works.
- **The network is not GPL merely because GPLv3 code trained it.** A program's licence does not reach
  the data it processes. `pawnstar-v20.bin` is distributed under this repository's own licence by
  choice.

## Provenance of earlier networks

Pawnstar networks up to and including **v12** were trained on self-play data generated by
**PlentyChess**, by Yoshie2000 — approximately 6 billion positions. That data is no longer
used: networks from **v20 (release 2.0.0)** onward are trained entirely on Leela Chess Zero
self-play data.

The attribution is kept here deliberately. Those networks were measurably stronger for having been
trained on that data, and the record should show where they came from. It is recorded in
[../THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md) as well, marked withdrawn.

**No network in the current release was trained on any PlentyChess data, and every network that was
has been withdrawn.** `pawnstar-v12.bin` and every net before it are removed from the source tree, and
every release that shipped them has been deleted - so no binary distributed from this repository
contains an evaluator trained on that data.

## The two network shapes, and the features that pick one

Five engines are being unified onto one NNUE evaluator (skill `reckless-nnue`). The shared
architecture — **this build's default since release 2.0.0** — adds two things to the shape the
retired v12 net was trained for. Both were measured in zenith on this hardware, SPRT-gated, and
both only paid past ~1.4B training positions — at 190M they were neutral or negative, which is
why v12 had neither:

| | v12's shape (retired) | the shared shape (**default**) | measured |
|---|---|---|---|
| horizontal king mirroring | off | **on** — a perspective whose own king is on files e–h is mirrored (`square ^ 7`) before indexing | **+14.3 Elo** fixed depth |
| material output heads | 1 | **8**, selected by `(piece_count - 2) / 4` | **+14.7 Elo** fixed depth |
| king bucket map | `half * 4 + file / 2` (file-*pairs*) | `half * 4 + min(file, 7 - file)` (per-*file*) | |
| `king_bucket_map_crc` | `0xCC6DDB5DAF0AB18D` | `0x0A20060D4E9586E0` | |
| `format_version` | 1 | **2** | |
| payload bytes | 12,589,060 | 12,617,760 | |

Mirroring is worth more than its Elo suggests: halving the king-placement space gives **twice the
effective data per bucket at the same file size**, so it is a data multiplier as much as an Elo add.

**Either shape builds from this one tree.** The knobs are the Cargo features
`nnue-king-mirroring` and `nnue-output-buckets-8`, together `nnue-shared-shape`, and **both are now
in `default`**, so a plain `cargo build` is the shared shape — which is the shape the shipped net
needs. The retired v12 shape is what is left when the defaults are dropped, and it keeps a **target
directory of its own**: not only to keep the two builds apart, but because MSVC's linker has been
seen to fail with `LNK1201` on a PDB the other feature set wrote, which it did again when these
defaults were flipped. Delete `<target>/release/deps/*.pdb` and re-run.

```bash
CARGO_TARGET_DIR=target-v12shape cargo test --release --no-default-features --features debugx
```

Note what `--no-default-features` now costs: it drops the NNUE shape as well as DEBUGX, so a
DEBUGX-free build **of the shipped shape** is `--no-default-features --features nnue-shared-shape`.

Expect the v12-shape build to refuse `nnue/pawnstar-v20.bin` — `net '...' refused:
format_version is 2 in the file but 1 in this engine`. That is the container working, not a fault:
**no net of that shape is in the tree any more**, v12's having been removed when 2.0.0 shipped. The
suites that need a *trained* net skip there and say so, exactly as they skip when the net file is
absent; `nnue_incremental_test` instead builds **its own synthetic net** at whatever shape the
build was configured for, which is what keeps the retired shape testable with no net of its own
and what tested the shared shape before any net existed for it.

**A shape change is an evaluation change.** It moves the bench signature and breaks parity with
`pawnstar` and `pawnstar-go` unless all three move together: the flip to these defaults landed in
all three with the same net and the same new signature, which is the only way it is allowed to
happen. The mirrored map also changes what a bucket *means* rather than only how many there are,
which by the container's own rule makes it a format change — hence `format_version` 2, **derived
from the mirroring switch and never hardcoded**, in every port.

### Why mirroring needs its own refresh rule, and why getting it wrong is silent

A perspective can be updated incrementally only while its weight bank, its square flip and its colour
flip all stay put; if any changes, every feature row it reads moves. Before mirroring there was one
way for that to happen, a king crossing a bucket boundary, and the code compared bucket indices.
Mirroring adds a second, and the two are not the same: on the mirrored map a king stepping
**d1 → e1 keeps bucket 3** (file 3 and file 4 both mirror to file 3) while its square flip gains the
file flip. A comparison of buckets alone would diff an accumulator whose whole basis had just changed
— no crash, no assertion, just a wrong evaluation. So the three live together in one
`nnue::Perspective`, compared whole, and `nnue_incremental_test` crosses each boundary on purpose and
reports how many plies forced a refresh, so a case that quietly stopped crossing anything cannot
pass. Narrowing the comparison back to the bank alone makes that suite fail on the first ply of its
first line, naming `white(bank=2304 flip=7)` — same bank, different flip — while the half-boundary
lines still pass, which is how the test was checked.

### The synthetic net's cross-port node-count signature

This gate was built when the shared shape had no net and `bench` could not run there. It is kept now
that v20 exists, because it is the one signature that is **independent of which net is shipped**:
`bench` locks the three ports together over the shipped net, this locks them over a net generated
from nothing, so a net change and a code change cannot be mistaken for one another. It is also the
only node-count gate the **retired** shape has, that shape having no net of its own any more
(at a shape whose net the engine refuses `bench` cannot run at all, and over random weights a
depth-13 search barely prunes and does not finish in any useful time).

The signature is six fixed-depth searches over the **synthetic net**, whose bytes are identical on
every platform and in every port (SHA-256
`4abfdb7bf3f6753fb53d8fed3b524750f7c06031cd5464445f18075f8ad4871b`, 12,617,824 bytes — the same
file the C++ engine's `test_nnue_incremental --write-synthetic-net` writes).

[`tools/new-shape-signature.sh`](../tools/new-shape-signature.sh) is that gate, and it is **committed
byte-identical in `pawnstar`, `pawnstar-rs` and `pawnstar-go`, and a fourth time in `nnue-training` as
`pipeline/new-shape-signature.sh`** (blob `46aad8fe29e64d937e63851a8afba284abc6c7a2`): the six expected
results live in it and nowhere else, so `diff` between the four copies is the whole audit and there is no second copy of
the numbers to drift — this file used to hold one, and a second copy of this repository's *bench* golden
once sat in CI and silently went stale for three commits. The `shape-signature` CI job runs it on every pull
request.

```bash
cargo build --release --bins        # since 2.0.0 the default shape IS the shared shape
target/release/write_synthetic_net synthetic-net.bin
tools/new-shape-signature.sh --hash 64 --net synthetic-net.bin --depth 8 target/release/pawnstar
```

The script's own header used to say the shape lives behind a switch that defaults off, which stopped
being true at release 2.0.0. It was corrected on 2026-10-30 — in all **four** copies at once, which is
the only way that file may ever be changed, its byte-identity being what the audit consists of.

It asserts the net's size, SHA-256 and RNNUE1 header — including `format_version` 2, `payload_bytes`
12,617,760 and `king_bucket_map_crc` `0x0A20060D4E9586E0` — **before** searching it, so a drifted
generator fails as a drifted generator instead of reading as a search regression. `--hash` is mandatory
and deliberately not defaulted, and its value is printed beside every node count: table size changes the
collision pattern and so the node count at a fixed depth, which is how `pawnstar-go`'s 512 MB default
stayed invisible for five months against this port's 64 MB. The numbers were reproduced by all three
ports at `Hash 64` — C++ (clang 22 on Windows, clang 18 on `reckless-ci-lin-2`), Rust and Go.

The last two of the six positions put the kings on d1/d8 and e1/e8, either side of the mirror boundary,
so the search spends its time in positions whose perspectives keep crossing it — the case that is silent
when the refresh rule is wrong.

Two traps the script handles, and that anybody reading these numbers out of the engine by hand must
handle too: `quit` straight after `go` cancels the search but still prints a `bestmove`, so wait for the
`bestmove` before sending `quit`; and **two line types begin `info depth N`** — only the completed
iteration carries `nodes`, so a `currmove` report reads as a missing node count on a search that
actually finished.

**This file is a shared asset, not a Rust artifact.** Everything about producing a net — the
bullet trainer setup, data pipeline, quantisation, verification, SPRT testing, and the full
net-shipping checklist — lives in the C++ repository (`nnue/README.md` §6–7 and
`nnue/int8_quant_study.md` in [pawnstar](https://github.com/jonny-reckless/pawnstar), the reference implementation). Nets are
trained once and shipped to both engines.

## Shipping a new net to this repo

After following the C++ checklist (train → `stamp_net` → regenerate references → SPRT):

1. Replace `nnue/pawnstar-v20.bin` (the loader validates the stamped header against the engine
   constants in `src/nnue.rs`, and the header's king-bucket map checksum against the checksum of
   this engine's own `KING_BUCKET_MAP`; an arch change means updating those constants in lock-step
   with the C++ `nnue.h`, the Go engine, and the container's `format_version` if a bucket's
   *meaning* changes). Name it for the release — `v12` was version 1.2 and `v20` is 2.0 — and
   **verify its SHA-256 before committing it**, against the value the three repositories agree on:
   every other check in the tree passes against whatever net happens to be there, so a wrong net
   ships silently.
2. Copy the regenerated `test/nnue_reference.txt` from the C++ repo to `tests/nnue_reference.txt`
   (the bullet cross-check evals are net-specific). It is checked out `-text`, so it stays
   LF-terminated. v20's 250 agree with the engine's `evaluate_exact` to **0 cp**; the int8 bound in
   `tests/nnue_test.rs` is a per-net measurement too, 40 cp for v20 against 26 for v12.
3. Update the Bratko-Kopec accepted-move sets in `tests/bratko_kopec_nnue_test.rs` to match the
   C++ `test/bratko_kopec_nnue_test.cpp` regeneration (must solve 24/24 at depths 8–11).
4. Re-bless `tests/bench_golden_test.rs`: run the parity diff against the C++ engine first
   (README.md, "Reproduce the parity check"), then record the new per-position node counts, best
   moves and total.
5. `cargo build --release` re-embeds the net (`include_bytes!` — no stale-embed pitfall, unlike
   the C++ `.incbin`, but the binary only picks the new net up on rebuild).
